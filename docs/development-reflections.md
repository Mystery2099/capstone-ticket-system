# Development Reflections & Lessons Learned

**Project:** Capstone Ticket System  
**Course:** CISY 8503 — Open Source Database Lab

## Introduction

When I started working on my ticketing system, I wasn't expecting the database itself to be the hardest part. I've worked with relational databases, SvelteKit, and Drizzle before, so a lot of the underlying concepts were already familiar to me. What I underestimated was just how much work exists around the features people actually see. Creating tickets, assigning them, changing their status, and leaving comments are relatively straightforward; making all of that secure, reliable, recoverable, and pleasant to use is a much bigger undertaking.

I also approached this project differently from some of my earlier work. I planned the application and worked through UI designs before implementing it, and I made heavy use of AI coding agents as development progressed. That made the work considerably faster, but it also shifted a lot of my attention toward architecture, deciding what the application should do, and checking whether implementations actually met those decisions. Some of what I learned was technical, but a lot of it came from having to take responsibility for the application as a whole instead of just getting individual features working.

## Authentication: Easier to Build Than to Own

One of the first things that surprised me was Better Auth. The initial integration with SvelteKit was only around 65 lines across four files, which is remarkably little wiring for something that handles sessions, cookies, and authentication routes. Disabling public registration was a single configuration flag, and adding authenticator-based multifactor authentication was even more surprising. The `twoFactor()` plugin handled enrollment, recovery codes, and the sign-in flow, leaving me to build the QR code interface and integrate it into the experience.

That convenience didn't make me regret using Better Auth, but it did change how I think about authentication in a production application. I eventually had to disable the admin plugin's routes because they bypassed rules my application enforces, such as preventing the last enabled administrator from being removed or disabled. Account changes needed to happen through my own transactions, and rate limiting, production checks, and emergency account recovery were also responsibilities I had to handle. Better Auth took care of much of the authentication machinery, but I was still responsible for the security policies and operational procedures around it.

For this project, I think it was the right choice, and I would use it again in a similar situation. For an actual organization, though, I'd rather integrate with an identity provider that the organization already manages, ideally through OIDC, while retaining application-specific roles and permissions in my own database. If there wasn't an existing provider, I'd consider a managed identity service rather than take on password policies, account recovery, and MFA operations myself. I also use authentik for self-hosting, although self-hosting an identity provider obviously doesn't eliminate the responsibility of operating it.

## PostgreSQL, Drizzle, and Making Database Concepts Hold Up

PostgreSQL didn't really introduce me to new database concepts. I already understood foreign keys, constraints, transactions, and relational modeling, but this project made me apply them in situations where they actually mattered. Things like priority constraints, preventing blank text, case-insensitive uniqueness through a `lower()` expression index, and restrictive foreign keys weren't just things to mention in a schema diagram. They became part of what kept the application from accepting invalid data, even when something slipped past application-level validation.

I also had to think more carefully about which responsibilities belonged in PostgreSQL and which belonged in the application. I chose not to use row-level security for this project because SvelteKit is the only layer that accesses the database, and authorization is enforced before data reaches the client. At the same time, the running application uses a restricted PostgreSQL role rather than the account used for migrations. That means the database still provides another layer of protection, including explicit grants and restrictions on operations the application should never perform.

Drizzle remained one of my favorite parts of the stack. I've used it for a while, and I like that the schema and TypeScript types remain connected without forcing me to abandon SQL when a query gets complicated. The ticket search implementation is a good example: it combines typed queries with PostgreSQL's full-text search, weighted `tsvector` documents, relevance ranking, trigram-based typo matching, and highlighting. Drizzle's tagged SQL templates let me use the database features I wanted without fighting the ORM, while tracked migrations made schema changes reasonably predictable.

The biggest new lesson wasn't about transactions themselves, but about concurrency. I already knew that changes belonging to one logical operation should either succeed or fail together. What I hadn't needed to think about as deeply was what happens when two people try to perform those operations at the same time. Ticket updates lock the affected row for the transaction, while protecting the last enabled administrator requires locking the relevant administrator records before checking whether a change is allowed. Even creating the first administrator needs protection against two setup processes racing each other. Those situations made database locking feel much less theoretical.

My database preferences haven't really changed. I still prefer SQLite for smaller, single-user, or self-hosted applications where having one database file and almost no operational overhead is a huge advantage. For a multi-user application like this, PostgreSQL is still my first choice because of the combination of concurrency controls, indexing, search capabilities, and administrative permissions. This project mostly reinforced why I already felt that way.

## Permissions and the Less Obvious Ways Data Can Leak

The permission system became more involved than I'd originally planned. I started with the expected requester, agent, and administrator roles, then moved toward database-backed roles with configurable capabilities rather than scattering checks for specific role names throughout the application. That increased the amount of work considerably, since changing and deleting roles introduces its own problems. For example, deleting a role used by existing accounts requires reassignment, and making sure there is always an enabled administrator becomes more complicated once the roles themselves can change.

I still think that complexity was worth it. Checking whether someone has a particular permission is clearer and more flexible than assuming a role name always implies the same set of capabilities. It also makes the rules easier to inspect, test, and change without rewriting authorization logic throughout the codebase. Some capabilities, such as managing the entire administration system, remain deliberately reserved for the built-in administrator role.

The most important security lesson came from internal notes. Hiding an internal note from the ticket conversation is only the obvious part of the requirement. The same information could accidentally appear in search documents, highlighted snippets, activity history, previews, or counts, even when the main interface looks correct. I had to treat every place that assembled or returned ticket information as a potential leak path. The approach I settled on was to filter information according to the user's permissions before serializing it, rather than trusting the frontend to hide anything sensitive. Similarly, attempts to access someone else's ticket return a not-found response so the application doesn't reveal which ticket numbers exist.

I already cared about security before starting this project, partly because of my experience with cybersecurity coursework and the National Cyber League. What changed was seeing how many small decisions had to agree for the system to remain secure. A good permission check in one component doesn't mean much if a different query accidentally exposes the same data somewhere else.

## SvelteKit, Architecture, and Keeping the Code Understandable

SvelteKit held up very well as the application became more complicated. I actually had agents prototype the project in both SolidJS and SvelteKit, and the SolidJS version needed noticeably more scaffolding to reach a comparable result. That was a big reason I stayed with SvelteKit, and I haven't regretted it. Svelte 5's runes also worked well for shared state such as drafts, while the ticket list could be virtualized and Tiptap could be integrated without having to change frameworks or invent a completely different application structure.

The architecture itself wasn't some new revelation to me. Keeping database operations, authorization, search, ticket commands, and UI components separated already felt like the right way to build the application. What became clearer was how important those boundaries were when multiple coding agents were working on different parts of the project. I spent time directing module boundaries, naming, and refactors so an agent could extend one area without having to untangle unrelated code or duplicate security rules somewhere else.

That wasn't just about making the repository look neat. Shared authorization helpers, focused server modules, and clear documentation made it easier to review changes and catch decisions that didn't belong in a particular layer. There were still smaller issues with form state and hydration, particularly in automated browser tests, but nothing that made me reconsider SvelteKit. I've since chosen it for another course project, which probably says more about my experience than any framework comparison I could write.

## The UI Was Worth the Time

I spent far more time on the interface than I did on the database, and I'm still happy with that decision. The database work was honestly the easier half for me, whereas getting the desktop and mobile layouts, themes, contrast, interactions, and smaller details right took a lot of iteration. We had mockups before the implementation started, so I wasn't making every design decision while also trying to write the application. That helped, although it also meant I had a pretty clear picture of how polished I wanted the final result to be.

The UI is easily the part I'm most proud of. I still open the application sometimes just to look at it, and I particularly like how the mobile layouts and themes turned out. One of my favorite smaller details is the draft and unsaved-changes handling. Someone can write a long reply and not lose it because a request failed or they navigated away, which seems like a small thing until you've experienced an application that throws away what you were typing.

Another detail I'm particularly happy with is the MFA enrollment flow, especially the step that asks users to confirm they've saved their recovery codes. Those kinds of interactions don't make for flashy feature lists, but they're part of making software considerate of the person using it. The UI also helped stress-test the underlying data model: previews, counts, private notes, editing, and search all became more complicated once I had to show them correctly in an actual interface.

## Testing, Including Testing the Tests

AI agents wrote the automated tests in this project, but that doesn't mean I accepted everything they generated. One issue I repeatedly pushed back on was excessive or redundant coverage, since agents can generate a surprising amount of testing code that doesn't really tell you anything new. I added guidance to keep tests focused and relatively minimal, and I removed some that weren't earning their maintenance cost. My goal wasn't the largest possible suite; it was a suite that checked the behaviors we actually needed to rely on.

Testing still paid off in ways I hadn't predicted. End-to-end tests exposed a real admin-form state issue involving hydration, while the MFA tests uncovered a problem in the testing infrastructure itself. The test harness used an independently implemented TOTP generator, which was useful because it wasn't simply repeating the application's implementation. However, the enrolled secret also needed to persist across Playwright workers; otherwise, workers could fail for reasons unrelated to the feature being tested. That was a useful reminder that test code can have state and bugs of its own.

The verification process eventually included linting, type checking, unit tests, builds, and end-to-end tests against an isolated database, with pull-request checks and a deployment health check as additional gates. Even then, a passing suite didn't mean every decision was good. One change introduced a 15-minute session requirement for administrative actions that didn't match my intended policy. I removed that extra restriction while retaining the existing administrator MFA requirement. Passing tests hadn't established that the policy itself was appropriate. That experience reinforced something important: tests can show that software behaves as specified, but they can't decide whether the specification makes sense.

## Azure and the Difference Between Code and Operations

Azure was one of the more frustrating parts of the project, although not because the application itself was particularly difficult to deploy. The problems tended to involve platform rules that didn't exist in my local environment. For example, the PostgreSQL migration for trigram-based search worked locally but failed on Azure because the `pg_trgm` extension needed to be explicitly allowed in the server configuration. Another failure came from the hosted database being behind the application code, which surfaced as a missing column during sign-in. Both issues were reminders that schema changes and deployment order are operational responsibilities, not just development tasks.

There were other details to deal with, including database firewall rules, the application's published outbound IP addresses, startup behavior, and preserving the dependencies needed for deployment. I also separated the database account used for migrations from the restricted one used by the running application, and documented the steps required to reapply grants after relevant schema changes. Those decisions made the deployment process more involved, but they also made it easier to explain exactly what the application is allowed to do and how it should be recovered if something goes wrong.

I didn't enjoy working in the Azure portal, so I eventually let a browser-use agent handle much of that interface work. GitHub OIDC federation also made deployment credentials more manageable without storing a long-lived client secret. I'm glad I got the application deployed, but the experience reinforced my preference for self-hosting, where I generally feel more comfortable inspecting the system and its errors directly. Azure worked for what I needed; it just didn't make me particularly enthusiastic about using it again.

## AI-Assisted Development and My Role in the Project

AI agents implemented a substantial portion of this application, and I don't want to pretend otherwise. I tried doing more of the work manually at first, but for a codebase of this size, directing agents was considerably more efficient. My contribution shifted toward defining requirements, planning the architecture, deciding security policies, reviewing behavior, debugging problems, and verifying the results. I also got better at choosing different agents and models for different kinds of work, rather than expecting one tool to handle everything equally well.

The agents were extremely useful, especially for work I wouldn't have enjoyed writing by hand, such as the MFA end-to-end test infrastructure, operational scripts, and repetitive implementation details. But they also introduced unnecessary complexity and sometimes made decisions I didn't ask them to make. The invented session rule, role-name checks mixed into capability-based authorization, and form-state bugs are all examples of why I couldn't simply treat generated code as correct because it compiled and passed tests. I had to review the actual behavior and make sure it matched what I wanted the application to do.

There's also a personal tradeoff here. I enjoy programming, and realizing that writing a feature myself was often the less efficient option honestly stung a little. I don't want my role to become sitting around telling agents what to do while never touching code. What I've started doing instead is spending my own programming time where I feel it matters most, particularly around difficult UI states, transactions, security boundaries, and other areas where I want direct control. The agents can handle a lot of the implementation, but I'm still the developer responsible for the decisions and the result.

## What I'd Do Differently

If I started the project over tomorrow, I'd keep almost all of the major decisions. I'd use the same general stack, keep the configurable permissions, require administrator MFA, and preserve the operational safeguards. Those features cost more time than a minimal classroom project needed, but they weren't accidental additions. I tried to keep the scope deliberate by documenting what was excluded, including email integration, attachments, self-registration, and other features that would have made the project much larger.

The most significant structural change I'd make is supporting assignment groups or teams from the beginning. Assigning a ticket to one individual works for a small demonstration, but it becomes awkward once multiple people share responsibility for a support queue. In-app update notifications and a personalized inbox are already implemented. I also have ideas such as temporary passwords, self-service password resets, ticket-level read/unread tracking, and further improvements to the inbox. Those are things I'd consider adding later, not evidence that the original project was designed incorrectly.

If anything, my approach to scope became more deliberate. I'm comfortable adding complexity when it solves a real problem, but an expansion should come with the documentation, tests, and operational thinking needed to support it. Otherwise, it's probably better to simplify the feature or leave it out. I'd rather finish fewer features properly than have a larger application full of half-complete ideas.

## Final Reflections

If I had to summarize what I learned for Professor Enke, I'd say that the biggest surprise was where the complexity actually lived. The visible ticketing features were only a fraction of the work. The much larger part involved accounts, permissions, private information, audit history, concurrency, recovery, deployment, and all the details people reasonably expect to work without thinking about them. I knew about most of those topics beforehand, but this project made me put them together into a system rather than treating them as separate concepts.

I also came away with a better understanding of how I want to approach larger projects. Planning the architecture and interface before implementation helped, and AI agents let me move much faster than I could have by writing every line myself. At the same time, they made it even more important for me to define what correct behavior meant and verify the parts that carried the most risk. The project strengthened my confidence in carrying an application from an initial idea through implementation, testing, deployment, and recovery, without convincing me that passing tests or having a polished interface automatically makes software ready for any production environment.

I'm proud of what I built, especially the interface and the attention paid to things users usually only notice when they go wrong. I wouldn't hand this exact deployment to a real college help desk tomorrow; I'd want directory-based identity, stronger hosting and monitoring, and an independent security review first. But I do think it has become a real, coherent system rather than just a database assignment with a frontend attached. More than anything, that's what I'll carry into the next project: building the visible feature is one part of the job, and taking responsibility for everything around it is the rest.
