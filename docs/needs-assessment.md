## Introduction

For my Open Source Database Lab, I plan to build a web-based support ticket system for a fictional small IT support team. Someone with a problem should be able to submit a ticket, and support staff should be able to organize the request, respond, and track it until the issue is resolved. The database work involves the relationships and rules behind those interactions; users need access to the appropriate tickets, status changes need to follow the workflow, and the history needs to preserve what happened.

I am writing this assessment before starting the build, so that the design and requirements have a clear reason behind them and the project does not grow in directions that do not serve the lab. Some decisions are still open, and I have tried to say so where that is the case rather than guess. I am using the six-step needs assessment framework from my class notes, covering objectives, stakeholders, existing workflows, requirements, gaps and costs, and the action plan. Because the support environment is fictional, the needs discussed here come from the intended workflow and my familiarity with IT support; they are not findings from interviews or surveys at an actual organization.

## 1. Objectives and scope

The main objective is to give requesters and support staff one place to manage requests without losing track of who is responsible, what has been tried, or whether an issue is still waiting for attention. A requester should be able to submit a problem and follow its progress, while staff need an organized queue where they can assign work, communicate with users, and record internal troubleshooting. Administrators need to manage accounts, roles, and ticket categories through the application instead of making changes directly in the database.

For the lab, the application also needs to demonstrate how PostgreSQL supports those workflows. I expect the schema to include tables for accounts, roles, categories, tickets, comments, and activity events, with foreign keys, unique constraints, and other database rules helping preserve consistency. Transactions matter here because a ticket update and its corresponding history entry should either both succeed or both fail; otherwise, the history could disagree with the current record.

To keep the goals measurable, I will consider the project successful if I can show a few specific things on a hosted copy of the application. A requester should create a ticket, an agent should find and assign it, and both people should see only the parts of the conversation meant for them. Staff should be able to leave an internal note that the requester cannot retrieve through the ticket page, search, or a direct request. A ticket should move through its lifecycle to Resolved, the requester should be able to reopen it, and reopening a Closed ticket should require elevated permission. Every ticket change should have a matching history entry, and a failed write should leave neither the change nor the entry behind. An unauthorized operation and an invalid reference should both be rejected. Finally, a backup of the database should restore into a separate database, and the application should still work against it.

The scope is intentionally smaller than a commercial help desk platform. Email-to-ticket integration, multi-organization support, complex reporting, push notifications, and automated workflows are outside the project's requirements. I am also leaving out image uploads and other attachments for now. Screenshots would be useful for troubleshooting, but storing files safely is a project of its own, and I would rather decide on it after the core workflow is working. I want a complete, understandable system for a small support team, without trying to recreate ServiceNow or Zendesk.

On compliance, the system is meant for general IT support requests, not health records, payment data, or other regulated information, and all sample accounts and tickets will be fictional. That keeps the project out of formal regulatory requirements. Tickets can still contain personal details, though, so access control and data protection need to be treated seriously anyway.

## 2. Stakeholders and user needs

The primary stakeholders are requesters, support agents, and administrators. They will use the same application but need different information and capabilities. Those differences affect both usability and security, since hiding a button does not protect information that a user should not be able to retrieve.

A requester needs a simple way to describe a problem, choose an appropriate category, and find their existing requests. They should be able to follow public responses and changes to their ticket without understanding how the support team organizes its work. Feedback should make it clear that a message was saved, and a requester should be able to reopen an issue marked Resolved if the problem was not actually fixed.

Support agents need a broader view of incoming work, including unassigned tickets and requests that need attention. They should be able to assign requests to eligible staff, adjust priorities or categories, and add public replies or private internal notes. Search should help them find a ticket by its number, subject, description, requester, or conversation content, while still respecting the user's permissions. That would be more useful during troubleshooting than relying on a single list ordered by creation date.

Administrators need to create and manage accounts, disable access when appropriate, maintain categories, and decide what each role is allowed to do. I am starting from three roles: Requester, Agent, and Administrator. The simplest approach would be to hard-code what each one can do, but I am leaning toward storing roles in the database with a list of capabilities, so an administrator could adjust a role or add a new one without a code change. Either way, the server should check what a role is permitted to do rather than trusting its name, and there needs to be some safeguard so an administrator cannot accidentally remove their own access. Flexible roles would add permission combinations to test, so I want to get the fixed version working first.

Professor Enke is another stakeholder because the lab needs to demonstrate database design and operation. He needs to be able to inspect the structure, understand the relationships, and see the application handle realistic workflows. My first proposal was a desktop application, but Professor Enke asked for a web application instead. That also works better for the other stakeholders, since requesters and staff may want to check a ticket from a phone, and one responsive web application can cover both without separate native clients.

## 3. Existing workflows and technology

There is no existing company's workflow to audit because the support team is fictional. The problem being addressed is support requests arriving through scattered conversations, such as email, chat messages, and someone stopping by a desk, where information can get buried and responsibility becomes unclear. That is the bottleneck the system targets: nobody can easily tell which requests are still open or who owns them. A ticket system gives each request a consistent record with an assigned person, current status, and conversation history. This describes the workflow the application is intended to improve, without claiming that a measured bottleneck was found at a particular organization.

I plan for the ticket lifecycle to have five states: Open, In Progress, On Hold, Resolved, and Closed. New tickets should begin as Open, and requesters should be able to reopen their own Resolved tickets. Closed tickets should stay read-only until someone with elevated permission reopens them. These rules define what each state allows and prevent ordinary users from silently changing administrative decisions.

Each ticket's conversation will contain public comments and internal notes, with different access rules for each. Public comments are shared with the requester and support staff, while internal notes are limited to authorized staff. That means the server has to leave private notes out of everything a requester can see, not only the ticket page but also search results, previews, and counts. Ticket changes and their history entries should be written in the same transaction so that the history reflects what actually changed.

Since this is now a web application, my original Kotlin plan no longer fits, so I looked at options that keep the server and interface together. I plan to use SvelteKit with TypeScript and Tailwind CSS. SvelteKit can serve both the pages and the server code from one application, which keeps the database entirely on the server; the browser should never receive database credentials or connect to PostgreSQL directly. For accounts I plan to use Better Auth rather than writing my own password hashing and session handling, since mistakes there are easy to make and hard to notice. It also supports authenticator-based MFA if I get to it. For the schema, I am planning to use Drizzle ORM, which sends parameterized SQL and generates migration files I can read before applying them. I would also like to try PGlite, an embedded version of PostgreSQL, for local development, so I do not have to keep a database server running on my laptop.

For hosting, I plan to use Azure, mainly because the college gives us some free Azure usage through Azure for Students. I have not deployed anything to Azure before, so I also see this as a chance to try it. Azure App Service can run the application, and Azure Database for PostgreSQL provides a managed database that handles patching and automated backups for me. Hosting in the cloud rather than on a machine I manage myself also means Professor Enke can reach the application without being on my network. The tradeoff is less control over the environment and some possible cost once the free usage runs out, which I cover in section 5.

For the interface, I want something that feels like an email client, because that would make the ticket system simple and familiar, especially for people who are less technically inclined. On desktop, I am picturing a sidebar, a ticket list, and a reading pane, similar to Gmail; on phones, it should probably show one page at a time. I plan to sketch desktop and mobile mockups before building anything. Those design choices support the ticket workflow, while the database operations remain the main purpose of the lab.

The relational model will need tables for accounts, roles, categories, statuses, tickets, comments, and ticket events, plus whatever tables the authentication library requires. Foreign keys should preserve the links between records, while unique identifiers and constraints prevent invalid states. Each ticket has one requester and at most one assigned staff member; comments and history entries belong to a specific ticket. Schema changes should go through tracked migrations rather than manual changes to the database.

Requesters should only be able to retrieve their own tickets, while agents and administrators have broader visibility according to their role. Staff-only notes must be filtered on the server before data reaches the browser. If I do add custom roles, testing will need to cover permissions after roles are created, edited, or reassigned. If I add MFA, I will also need recovery codes and some way for an administrator to be recovered from outside the application, so a lost phone does not permanently lock someone out.

Search should at least support ticket numbers, text in the subject and description, requester names, categories, and status filters. PostgreSQL has full-text search built in, and from what I have read, the `pg_trgm` extension could handle typos in subjects; I will need to check whether Azure allows that extension. Search results must follow the same access rules as normal ticket views.

On the server side, every change to a ticket should be validated and written together with its history entry in one transaction. Database credentials must stay on the server, and the hosted application should connect with a restricted account rather than the account that owns the schema. I also want automated tests for the database workflows and a written restore procedure that I have actually tried.

## 5. Gap analysis, risks, and budget

The gap between the current situation and the goal is the lack of one reliable place to track requests and their progress. The planned system closes it by keeping ticket records, assignment, status, public conversation, internal notes, and history in one application. Building those features is only part of the work, though; I also need to show that the behavior holds up under realistic permissions, failed writes, and a restore once the application is deployed.

Security is one of the largest risks because tickets may contain information that other requesters should not receive, and internal notes are specifically meant to stay private. A careless join or search query could expose that information even if the main ticket page looks correct. My checks need to cover direct requests by unauthorized users, search results and previews, role changes, disabled accounts, and attempts to reach private note content.

Database correctness needs similar attention. A status update that succeeds while its history entry fails would leave an incomplete record, and the same problem could affect assignment, category changes, or role changes. Transactions, database constraints, and targeted tests should reduce those risks, and I may need row locking if two people can update the same ticket at once. Testing should include invalid references and simultaneous requests, not only the expected successful workflow.

The total cost of ownership needs to stay reasonable for a college project. All of the software I plan to use is open source or free, so the cost is mainly hosting and time. Azure App Service has a free tier that should be enough for a demonstration, though it appears to sleep when idle and has daily limits, so the first request during a demonstration might be slow. The PostgreSQL server is billed separately, so I will need to check how much of it the college's free Azure usage covers and set a budget alert so costs do not surprise me. As a fallback, I should be able to run the whole demonstration locally. I also need to count the time spent configuring access, managing secrets, and testing restores, since those are part of the cost even if they are not visible features.

Scope creep is probably my biggest planning risk. Most of the wants in section 4 would make the system more useful and show off more of PostgreSQL, but each one adds behavior to test and could take time away from the core workflow. I want to prioritize correctness and a complete demonstration over email delivery, reporting, or automation. Attachments are the hardest call, since screenshots would genuinely help, but I do not think I can make file storage and its access control safe within the time I have.

The usability assumptions also need some validation. I will be designing for a small support team without testing the design with real users. If there is time, a short walkthrough with another student acting as a requester and someone else acting as an agent could reveal confusing labels, missing feedback, or unnecessary steps.

## 6. Action plan and roadmap

The first step is to turn these needs into a database design: the entities, their relationships, the ticket lifecycle, and the rules for note visibility. Desktop and mobile mockups and an architecture outline should follow, so the interface and the server responsibilities are settled before I write application code. I also want to review the scope with Professor Enke at this point, before anything is built.

Next, I will build the core workflow on that schema: accounts, ticket creation, assignment, status changes, public replies, internal notes, and the history written in the same transaction. Search and administration come after that. I want to write tests alongside the features rather than at the end, and keep a test and demonstration plan listing the checks to perform for requesters, agents, and administrators.

Once the core workflow works locally, I will deploy the application and database to Azure and check the hosted setup. I want separate database accounts for running migrations and for the application itself, so the running application cannot change the schema. I also need to confirm HTTPS, sign-in and sessions, and database network access on the hosted copy, since those may behave differently than they do locally.

The demonstration should include relational operations and recovery as well as the interface. Fictional tickets and accounts will let me show joins between users, tickets, categories, comments, and events, along with counts grouped by status or category. I also want to demonstrate an invalid operation being rejected, a transaction rolling back, and a PostgreSQL backup restored into a separate database. These checks are particularly relevant to the lab because they show the database behavior behind the web application.

Any time left after that should go to the wants in section 4, roughly in the order listed, and to usability fixes. Changes requested by Professor Enke should be recorded and weighed against the remaining lab requirements.

A few questions are still open. I need to confirm with Professor Enke whether the lab expects specific database features, a particular documentation format, or a minimum number of queries in the demonstration, and whether custom roles are worth including or a fixed set of three roles is enough to demonstrate authorization. On the hosting side, I still need to find out whether Azure's managed PostgreSQL allows the `pg_trgm` extension, how far the college's free Azure usage will go toward the database, and whether the free App Service tier is reliable enough for a live demonstration or I should plan to present locally.

## Conclusion

The ticketing system fits the Open Source Database Lab because its workflows depend on relationships and consistency that can be explained and demonstrated. Controlled access, ticket ownership, public and private communication, a defined lifecycle, and a history consistent with the database give me practical reasons to use PostgreSQL, constraints, joins, indexes, and transactions. Building the core workflow correctly, deploying it securely, and demonstrating it clearly should take priority over adding more functionality. If I can show that the data stays correct, permissions hold, and the database can be recovered, the project will meet the central goal of the lab while producing a reasonably usable support application.
