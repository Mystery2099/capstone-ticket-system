## Introduction

For my Open Source Database Lab, I plan to build a web-based support ticket system for a fictional small IT support team. Someone with a problem should be able to submit a ticket, and support staff should be able to organize the request, respond to it, and track it until the issue is resolved. The database work involves the relationships and rules behind those interactions; users need access to the appropriate tickets, status changes need to follow the workflow, and the history needs to preserve what happened.

I am writing this assessment before starting the build so that each part of the design has a reason behind it and the project does not grow beyond what the lab requires. Some decisions are still open, and I identify them where they come up instead of presenting them as settled. I am using the six-step needs assessment framework from my class notes, covering objectives, stakeholders, existing workflows, requirements, gaps and costs, and the action plan. Because the support environment is fictional, the needs discussed here come from the intended workflow and my familiarity with IT support; they are not findings from interviews or surveys at an actual organization.

## 1. Objectives and scope

The main objective is to give requesters and support staff one place to manage requests without losing track of who is responsible, what has been tried, or whether an issue is still waiting for attention. A requester should be able to submit a problem and follow its progress, while staff need an organized queue where they can assign work, communicate with users, and record internal troubleshooting. Administrators need to manage accounts, roles, and ticket categories through the application instead of making changes directly in the database.

For the lab, the application also needs to demonstrate how PostgreSQL supports those workflows. I expect the schema to include tables for accounts, roles, categories, tickets, comments, and activity events, with foreign keys, unique constraints, and other database rules helping preserve consistency. Transactions matter here because a ticket update and its corresponding history entry should either both succeed or both fail; otherwise, the history could disagree with the current record.

My class notes recommend setting measurable goals, so I have tied success to specific behavior on a hosted copy of the application. A requester should create a ticket, an agent should find and assign it, and both people should see only the parts of the conversation intended for them. An internal note should remain unavailable to the requester through the ticket page, search, and direct requests. A ticket should move through its lifecycle to Resolved, the requester should be able to reopen it, and reopening a Closed ticket should require elevated permission. Every ticket change should have a matching history entry, and a failed write should leave neither the change nor the entry behind. Unauthorized operations and invalid references should be rejected, and a backup of the database should restore into a separate database that the application can still use. Each of these can be demonstrated or tested, which makes them more useful to me than a general goal of building a working ticket system.

The scope is intentionally smaller than a commercial help desk platform. Email-to-ticket integration, multi-organization support, complex reporting, push notifications, and automated workflows are outside the project's requirements. I am also leaving out image uploads and other attachments for now. Screenshots would be useful for troubleshooting, but storing files safely involves its own storage, permission, and cleanup decisions, and I would prefer to consider them after the core workflow is working. I want a complete, understandable system for a small support team, without trying to recreate ServiceNow or Zendesk.

Compliance requirements also affect the scope. The system is intended for general IT support requests, not health records, payment data, or other regulated information, and all sample accounts and tickets will be fictional. That keeps the project outside formal regulatory requirements, although tickets in a real deployment could still contain names, contact information, and descriptions of personal problems. I think that is enough reason to treat access control as a central requirement even without a specific regulation applying to the data.

## 2. Stakeholders and user needs

The primary stakeholders are requesters, support agents, and administrators. They will use the same application but need different information and capabilities. Those differences affect both usability and security, since hiding a button does not protect information that a user should not be able to retrieve.

A requester needs a simple way to describe a problem, choose an appropriate category, and find their existing requests. They should be able to follow public responses and changes to their ticket without understanding how the support team organizes its work. Feedback should make it clear that a message was saved, and a requester should be able to reopen an issue marked Resolved if the problem was not actually fixed. Someone whose laptop still cannot connect to the network after a ticket was resolved, for instance, should not need to submit the same problem again and lose the earlier conversation.

Support agents need a broader view of incoming work, including unassigned tickets and requests that need attention. They should be able to assign requests to eligible staff, adjust priorities or categories, and add public replies or private internal notes. Search should help them find a ticket by its number, subject, description, requester, or conversation content, limited to the tickets they are permitted to see. During troubleshooting, that would be more useful than relying on a single list ordered by creation date.

Administrators need to create and manage accounts, disable access when appropriate, maintain categories, and decide what each role is allowed to do. I am starting from three roles: Requester, Agent, and Administrator. The simplest approach would be to define each role's permissions in the code, but I am leaning toward storing roles in the database with a list of capabilities, so an administrator could adjust a role or add one without a code change. In either design, the server should check what a role is permitted to do instead of relying on its name, and an administrator should not be able to remove their own access by mistake. Flexible roles would add permission combinations to test, so I want the fixed roles working before deciding whether the additional complexity is justified.

Professor Enke is another stakeholder because the lab needs to demonstrate database design and operation. He needs to be able to inspect the structure, understand the relationships, and see the application handle realistic workflows. My first proposal was a desktop application, but Professor Enke asked for a web application instead. That change also suits the other stakeholders; requesters and staff may want to check a ticket from a phone, and one responsive web application can serve both devices without separate native clients.

## 3. Existing workflows and technology

There is no existing company's workflow to audit because the support team is fictional. The problem being addressed is support requests arriving through scattered conversations, such as email, chat messages, and someone stopping by a desk, where information can get buried and responsibility becomes unclear. The main bottleneck is that nobody can easily tell which requests remain open or who is responsible for them. A ticket system gives each request a consistent record with an assigned person, current status, and conversation history. This describes the workflow the application is intended to improve, without claiming that a measured bottleneck was found at a particular organization.

I plan for the ticket lifecycle to have five states: Open, In Progress, On Hold, Resolved, and Closed. New tickets should begin as Open, and requesters should be able to reopen their own Resolved tickets. Closed tickets should stay read-only until someone with elevated permission reopens them. These rules define what each state allows and prevent ordinary users from silently changing administrative decisions.

Each ticket's conversation will contain public comments and internal notes, with different access rules for each. Public comments are shared with the requester and support staff, while internal notes are limited to authorized staff. The server therefore has to exclude private notes from everything a requester can retrieve, including search results, previews, and counts as well as the ticket page. Ticket changes and their history entries should be written in the same transaction so that the history reflects what actually changed.

Because the project is now a web application, my original Kotlin plan no longer fits, and I looked for a framework that keeps the server and interface in one project. I plan to use SvelteKit with TypeScript and Tailwind CSS. SvelteKit can serve both the pages and the server code from one application, which keeps the database entirely on the server; the browser should never receive database credentials or connect to PostgreSQL directly. For accounts, I plan to use Better Auth instead of writing my own password hashing and session handling, since mistakes in authentication code are easy to make and difficult to notice. It also supports authenticator-based MFA if time allows. I am planning to use Drizzle ORM for the schema because it sends parameterized SQL and generates migration files I can review before applying them. For local development, I would also like to try PGlite, an embedded PostgreSQL implementation, so I do not need to run a separate database server.

For hosting, I plan to use Azure, mainly because the college provides some free Azure usage through Azure for Students. I have not deployed an application to Azure before, so I also see the project as an opportunity to learn it. Azure App Service can run the application, and Azure Database for PostgreSQL provides a managed database that handles patching and automated backups. Hosting in the cloud also means Professor Enke can reach the application without it running on my own computer. The tradeoff is less control over the environment and some possible cost once the free usage is exhausted, which I discuss in section 5.

For the interface, I want something that resembles an email client, because that would make the ticket system feel simple and familiar, especially for people who are less technically inclined. On desktop, I am picturing a sidebar, a ticket list, and a reading pane similar to Gmail; on phones, the interface should probably show one page at a time. I plan to sketch desktop and mobile mockups before building anything. The interface matters to the people using the system, but the database remains the main focus of the lab.

The relational model will need tables for accounts, roles, categories, statuses, tickets, comments, and ticket events, along with whatever tables the authentication library requires. Foreign keys should preserve the links between records, while unique identifiers and constraints prevent invalid states. Each ticket has one requester and at most one assigned staff member; comments and history entries belong to a specific ticket. Schema changes should go through tracked migrations instead of manual changes to the database.

Requesters should only be able to retrieve their own tickets, while agents and administrators have broader visibility according to their role. Staff-only notes must be filtered on the server before data reaches the browser. If I add custom roles, testing will need to cover permissions after roles are created, edited, or reassigned. MFA would also require recovery codes and a way to restore an administrator's access from outside the application; otherwise, a lost phone could permanently lock someone out of the account that manages everyone else.

Search should at least support ticket numbers, text in the subject and description, requester names, categories, and status filters. PostgreSQL includes full-text search, and from what I have read, the `pg_trgm` extension could make subject matching tolerant of typos; I will need to confirm that Azure allows that extension. Search results must follow the same access rules as normal ticket views.

On the server, every change to a ticket should be validated and written together with its history entry in one transaction. Database credentials must stay on the server, and the hosted application should connect with a restricted account instead of the account that owns the schema. I also want automated tests for the database workflows and a written restore procedure that I have actually performed.

## 5. Gap analysis, risks, and budget

The gap between the current situation and the goal is the lack of one reliable place to track requests and their progress. The planned system closes that gap by keeping ticket records, assignment, status, public conversation, internal notes, and history in one application. Building the features is only part of the work, however; I also need to show that permissions hold, that a failed write does not leave partial changes behind, and that the data can be restored once the application is deployed.

Security is one of the largest risks because tickets may contain information that other requesters should not receive, and internal notes are specifically intended to remain private. A careless join or search query could expose that information even if the main ticket page appears correct. My checks need to cover direct requests by unauthorized users, search results and previews, role changes, disabled accounts, and attempts to reach private note content.

Database correctness needs similar attention. A status update that succeeds while its history entry fails would leave an incomplete record, and the same problem could affect assignment, category changes, or role changes. Transactions, database constraints, and targeted tests should reduce those risks, and I may need row locking if two people can update the same ticket at once. Testing should include invalid references and simultaneous requests as well as the expected workflow.

The total cost of ownership also needs to stay reasonable for a college project. All of the software I plan to use is open source or free, so the cost consists mainly of hosting and time. Azure App Service has a free tier that should be sufficient for a demonstration, although it appears to sleep when idle and has daily limits, so the first request during a demonstration may be slow. The PostgreSQL server is billed separately; I will need to check how much of it the college's free Azure usage covers and set a budget alert so the cost does not surprise me. As a fallback, I should be able to run the entire demonstration locally. Configuring access, managing secrets, and testing restores also take time, and I think that time belongs in the cost even though it does not produce visible features.

Scope creep is probably the largest planning risk. Most of the wants in section 4 would make the system more useful and demonstrate more of PostgreSQL, but each one adds behavior to test and could take time away from the core workflow. I want to prioritize correctness and a complete demonstration over email delivery, reporting, or automation. Attachments are the most difficult decision; screenshots would be helpful for IT tickets, but I do not think I can make file storage and its access control safe within the available time.

The usability assumptions also need some validation. I will be designing for a small support team without testing the design with representative users. If time allows, a short walkthrough with one student acting as a requester and another acting as an agent could reveal confusing labels, missing feedback, or unnecessary steps. That would give me a more specific reason for interface changes than my own impression of the design.

## 6. Action plan and roadmap

The first step is to turn these needs into a database design covering the entities, their relationships, the ticket lifecycle, and the rules for note visibility. Desktop and mobile mockups and an architecture outline should follow, so the interface and the server responsibilities are settled before I write application code. I also want to review the scope with Professor Enke at that point, before anything is built.

Next, I will build the core workflow on that schema: accounts, ticket creation, assignment, status changes, public replies, internal notes, and the history written in the same transaction. Search and administration will follow. I want to write tests alongside the features instead of leaving them for the end, and to keep a test and demonstration plan listing the checks for requesters, agents, and administrators.

Once the core workflow works locally, I will deploy the application and database to Azure and check the hosted setup. I want separate database accounts for running migrations and for the application itself, so the running application cannot change the schema. I also need to confirm HTTPS, sign-in and sessions, and database network access on the hosted copy, since they may behave differently than they do locally.

The demonstration should include relational operations and recovery as well as the interface. Fictional tickets and accounts will let me show joins between users, tickets, categories, comments, and events, along with counts grouped by status or category. I also want to demonstrate an invalid operation being rejected, a transaction rolling back, and a PostgreSQL backup restored into a separate database. Those checks show the database behavior behind the web pages, which is what the lab is meant to evaluate.

Any remaining time should go to the wants in section 4, roughly in the order listed, and to usability fixes. Changes requested by Professor Enke should be recorded and weighed against the remaining lab requirements.

A few questions are still open. I need to confirm with Professor Enke whether the lab expects specific database features, a particular documentation format, or a minimum number of queries in the demonstration, and whether custom roles are worth including or three fixed roles are enough to demonstrate authorization. On the hosting side, I still need to find out whether Azure's managed PostgreSQL allows the `pg_trgm` extension, how much of the database cost the college's free Azure usage will cover, and whether the free App Service tier is reliable enough for a live demonstration.

## Conclusion

I think a ticket system is a good fit for the Open Source Database Lab because nearly everything it does depends on related records remaining consistent. Who can see a ticket, who is responsible for it, which notes are private, and what happened to it over time are all questions the database has to answer correctly through its tables, constraints, joins, and transactions. My priority is getting the core workflow working and deployed before adding optional features. If I can show that the data remains correct, permissions hold, and the database can be recovered, the project will meet the goal of the lab while still producing a support application someone could reasonably use.
